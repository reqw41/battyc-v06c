# Исходный бюджет тяжёлого шага Batty 3+1

Этот отчёт относится к ROM до исправлений (`870b8de6…`). Актуальные результаты — в [THREE_PLUS_ONE_FAST.md](THREE_PLUS_ONE_FAST.md).

Замер неизменённых ROM на локальном vector06js: обычный Вектор-06Ц, 64 КБ, 3 МГц. Сцена: движущаяся бита, три шара, бонус, UFO. 65 управляемых игровых шагов, последние 45 — прогретые. Это тяжёлая контрольная сцена, а не доказанный максимум всех игровых ситуаций: попадания в кирпичи и дополнительные пули здесь не форсируются.

Единица — такт Вектора (`cpu.vcycles`, синхронизация машинных циклов с памятью), а не номинальный табличный T-state 8080 (`cpu_cycles`). Такой же счётчик использовали предыдущие замеры скорости. Результат точно совпадает с `measure-object-speed.js` для обоих ROM. Время выполнения самого JS не измеряется.

Процедурные группы ниже взаимно исключаются: вложенные процедуры, выделенные отдельными строками, из родителя вычтены. Вспомогательные вызовы входят в соответствующую группу. `MonoSingleCommit` не включает свои вызовы `MonoZeroRange`; IRQ внутри вывода вынесен отдельно. Логика и ожидание включают попавшие в них инструкции IRQ. Не следует суммировать inclusive-времена процедур из JSON.

## Сравнение предыдущего трёхплоскостного композитора и 3+1

Предыдущий вариант имел три видимые плоскости фона, но спрайты уже меняли только C/E. Его плоскость 8000 была скрытой RAM с кодом и кэшами. Эти записи не считаются записями в видимую видеопамять. В 3+1 плоскость 8000 видима и содержит белые спрайты; A/C/E содержат фон.

| Показатель | Предыдущий композитор | 3+1 |
|---|---:|---:|
| Средний шаг, инструкции | 160880.1 | 169186.3 |
| Логика | 22196.1 | 22186.8 |
| Весь вывод, включая IRQ в нём | 136498.5 | 145697.0 |
| SpriteCacheBuild, вызовов/шаг после прогрева | 0.000 | 1.756 |
| Записи в видимую VRAM, байт/шаг | 410.22 | 450.89 |
| Такты инструкций, непосредственно записывающих VRAM | 3281.8 | 3612.4 |

Чистая прибавка среднего шага: 8306.2 такта (5.16%). Логика практически совпадает. Вывод подорожал на 9198.5 такта; ожидание растра сократилось и частично компенсировало разницу.

## Где расходуются такты

1. Первый проход `MonoDraw` добавляет новые белые пиксели через OR. Он занимает 22706.0 такта. Сам по себе это дешевле предыдущего `CGShadeSaved` (42561.6 такта).
2. После первого прохода всё старое прямоугольное покрытие заново проходит через `MonoSelectCandidates`, `MonoComposeColumn`, `MonoSingleCommit` и очистку. Вместе с управлением проходом это 73570.9 такта без IRQ. Большинство перекрытых байтов пишется повторно. Старый `CGIsolated` выводил окончательные байты нового спрайта, а затем восстанавливал только уходящие края; при неизменном прямоугольнике также был отдельный быстрый путь.
3. Поиск кандидатов делает шесть обходов всех 11 описателей: 66 проверок за шаг. В этом наборе у всех 17.82 старых колонок ровно один кандидат; путь объединения нескольких новых объектов не выполнялся. Даже этот простой случай платит за универсальный расчёт колонок и повторный вывод.
4. Для бонуса и UFO имеется только по одному текущему сдвинутому кэшу на владельца. Все 1.756 прогретых промаха/шаг вызваны сменой сдвига; смены исходной картинки и высоты в этих промахах нет. Бонус: 0.889 сборки/шаг, 10830.7 такта inclusive; UFO: 0.867, 13044.4. Предыдущий вариант хранил восемь сдвиговых фаз отдельно для бонуса и врага; после прогрева сборок в этой сцене не было. Для 4.244 объектов/шаг 3+1 берёт готовую графику прямо из ROM.
5. Бита с чёрной обводкой остаётся исключением из одноплоскостного вывода: меняются белая плоскость 8000 и фон E. Первый проход: 180.78 записи в 8000 и 44.67 в E; второй: 180.78 и 44.67. Второй проход делает в среднем 210.18 повторных записей по адресам, уже затронутым первым проходом (225.44 разных адреса). В A/C движущийся вывод не пишет.

Инструкции непосредственной записи VRAM занимают лишь 2.14% шага. Это не вся цена вывода: чтение графики, OR, проверки биты, адресация, счётчики и ветвления учтены в процедурах выше. Поэтому снижение числа плоскостей не означает пропорционального ускорения всего шага. Здесь общее число записей даже выросло из-за повторного прохода.

## Контроль движения

Исходный стенд сдвигает объекты по `tick % 8` и имеет переход 7→0. Второй прогон использует плавную последовательность 0..7..0 без такого скачка. При ней предыдущий вариант: 155006.3 такта; 3+1: 169459.0. Замедление сохраняется; оно не объясняется одним искусственным скачком координаты стенда.

## Направление оптимизации

Первый приоритет — отдельный путь для изолированного объекта: конечные байты нового спрайта писать один раз, удалять только уходящие пиксели/края. Для пересечений оставить общий композитор. Простое пропускание второго прохода некорректно: первый OR сохраняет часть битов старого спрайта в перекрытии.

Второй — не пересобирать фазу бонуса/UFO при каждом сдвиге: несколько сохранённых фаз или готовые фазы в ROM с проверкой бюджета памяти. Полное устранение нынешнего `SpriteCacheBuild` само по себе оставит около 145325.8 такта/шаг, что всё ещё выше 119808. Одна работа с кэшем не обеспечит 25 Гц.

## Воспроизведение

```sh
node verify/profile-three-plus-one-budget.js
```

Рядом должен находиться прежний checkout `../vector06c-batty-three-plane`. Требуется локальный vector06js либо переменная `VECTOR06JS_ROOT`. Профайлер не меняет ROM. JSON содержит фазы, inclusive/exclusive-процедуры, трафик VRAM, причины кэш-промахов и все 65 шагов обоих вариантов в двух режимах движения. В каждом шаге проверены суммы фаз, процедур и групп вывода; в исходном режиме проверено точное совпадение с прежним стендом скорости.

SHA256 3+1: `870b8de67982c694229d54cbb591bde9c42099f9d16b2af8fdc6936b03af7732`. SHA256 предыдущего ROM: `05fefa2679e16e3edb2a2b63c31259e3b7b494d2397dc0b21932a033f7706ec4`.
